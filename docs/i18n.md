# Internationalization (i18n)

Hand-rolled, request-scoped i18n built into the core. No external library.

## How locale flows

1. `hooks.server.ts` resolves `event.locals.locale` per request:
   cookie `locale` → `Accept-Language` → site default → `en`, validated against
   the site's enabled locales. On `/admin` and `/user` routes, the signed-in
   user's own `users.locale` preference (profile page) wins.
2. `+layout.server.ts` forwards `locale`, `i18n: {defaultLocale, enabledLocales}`,
   and `currency` in layout data. `app.html` carries `lang="%lang%"`, rewritten
   by `transformPageChunk`.
3. Components read locale via stores derived from SvelteKit's `page` store —
   never a module-level "current locale" (Workers isolate safety).

## Using it

- **`.svelte` files:** `import { t, money, dateFmt } from '$lib/i18n'` →
  `{$t('cart.title')}`, `{$t('cart.itemCount', { count: n })}` (plurals via
  `.one`/`.other` key suffixes), `{$money(subtotal)}`, `{$dateFmt(ts, 'long')}`.
- **`.server.ts` files:** `createTranslator(locals.locale)`; call `formatMoney`
  / `formatDate` directly. Never use the stores in shared `.ts` modules.
- **Catalogs:** `src/lib/i18n/locales/<code>.json` — flat dot-namespaced keys,
  `{param}` interpolation. Adding a locale = add the JSON file, import it in
  `catalogs.ts`, add a registry entry. A key-parity test enforces coverage.

## Per-site language config

`site_settings` keys `i18n_default_locale` / `i18n_enabled_locales` via
`getLanguageSettings`/`updateLanguageSettings`. Admin UI:
**Settings → Languages**. The storefront `LanguageSwitcher` (NavBar config flag
`showLanguageSwitcher`) POSTs to `/api/locale`, which sets the httpOnly cookie
and the UI re-renders via `invalidateAll()`.

## Tenant content translations

`content_translations` (migration 0094) is a generic per-locale overlay:
`(site_id, locale, entity_type, entity_id, field) → value`. Source content is
never forked; missing fields fall back per-field to the source language.

- Widget text: `entity_type='page_widget'`, `entity_id=pageId`,
  `field='<widgetId>:<configPath>'` (page-scoped because seeded widget ids
  repeat across pages). Whitelisted config keys live in
  `src/lib/i18n/translatable.ts`.
- Products (`name`/`description`), site settings (store name/tagline/
  description → localized `${site.name}` substitution), content entries
  (schema-ready; editor still TODO).
- Render overlay: `translateComponents`/`translateProducts`/
  `translateGeneralSettings` in `src/lib/server/i18n/content-translations.ts`,
  wired into `routes/+page.server.ts`, `[...slug]`, `product/[id]`, and the
  root layout. No-ops for the default locale.
- Owner editing: **Admin → Translations** — side-by-side source→target forms
  per page/product/store details. Blank target = fall back. Orphaned rows are
  pruned on save and on page/product delete.

## Admin UI strings

The admin panel's own strings are being extracted incrementally into the
`admin.*` catalog namespace (dashboard/settings/products/orders first). The
admin locale is the per-user preference above, independent of site languages.

## Out of scope (future)

Per-locale WYSIWYG in the builder, machine-translation prefill, locale-prefixed
URLs (`/es/...`) for SEO, KV caching of translation lookups, per-tenant
overrides of catalog strings.
